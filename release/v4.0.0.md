# NekoKEM v4.0.0

## 简体中文

### 本版更新

v4.0.0 新增多人加密：一个文件最多可加密给 64 位接收方，每位接收方都能用自己的私钥解密，其他人无法解密。多人文件使用新的 NKEM v4 容器，桌面 GUI、Android 和 CLI 均可使用。Android 与所有 CLI/GUI 应用统一为 4.0.0，Core 升级为 4.0。

- **多人加密**：桌面 GUI 可在“公钥通讯录”页面勾选多位联系人后点击“加密给所选联系人”，也可在加密页的接收方列表中勾选；页面底部显示将写出 v3 还是 v4。Android 在“公钥通讯录”页面勾选“选为接收方”后点击“加密给所选接收方”，文件页列出全部接收方；勾选本身不会改变当前加密公钥。CLI 在原有加密命令后列出多个公钥即可：`nekokem encrypt hybrid <输入> <输出> <公钥1> <公钥2> ...`。
- **只选一位仍写 v3**：只加密给一位接收方时继续写出 NKEM v3，旧版本照常可读；选择两位及以上时写出一个 NKEM v4 文件。所有平台的解密都会自动识别 v3 与 v4。
- **任何一位出错都整体失败**：加密前，每位联系人都会重新读取，并由 Core 校验公钥与指纹。任何一位缺失、损坏或指纹不符时，整个操作失败且不产生输出，错误中会指出该联系人；**不会跳过任何接收方，也不会改用其他公钥**。重复的公钥、超过 64 位，以及共用任一密钥组件的两个公钥都会被拒绝。
- **NKEM v4 格式**：文件数据只用随机文件密钥加密一次。每位接收方各有一条记录，包含 X448 + ML-KEM-1024 封装和用 AES-256-GCM 包装的文件密钥；包装密钥由 HKDF-SHA512 派生，并参照 X-Wing 绑定 X448 交换。HMAC-SHA512 头部 MAC 承诺文件密钥，保证所有接收方解出相同内容。完整规范见 [`docs/NKEM-v4.md`](../docs/NKEM-v4.md)。
- **解密不暴露对应关系**：记录不含接收方标识。解密会尝试全部记录，匹配后也不提前停止；“不是给这把私钥的”和“文件被修改”报同一条错误，耗时也一致，从报错和耗时都看不出哪条记录属于哪把私钥。任一记录格式错误时整个文件被拒绝；加载私钥时会拒绝唯一的退化 X448 私钥。
- **发布前审计**：NKEM v4 在发布前经过两轮 AI 辅助安全审计。审计共提出 1 项 Medium、5 项 Info 和 1 项 Low，均已修复或写入文档。这**不等同于独立专业安全审计**。
- **测试**：新增 Core 多人加密测试（Linux ASan/UBSan 与泄漏检测、macOS、Windows），其中包括按规范独立编写的 v4 编码器、恶意文件构造、20 余处字节篡改和报错一致性检查。解析器与 AFL++ 种子覆盖 v4。CLI、桌面 Rust/Vitest/Playwright 测试和 Android API 26/35 设备测试覆盖多人加密。Android 通讯录界面测试改为读取前刷新无障碍节点、滚动后等待内容实际移动，修复慢速模拟器上的偶发失败。

### 兼容性提示

- NekoKEM **v3.3.2 及更早版本无法打开 NKEM v4 文件**。把多人加密的文件发给别人前，请确认对方已升级到 v4.0.0 或更新版本。
- v4.0.0 可以解密此前所有 NKEM v3 文件；NKEM v3、NKPR v1、公钥格式和指纹计算均不变，原有密钥可以继续使用。

### Android 升级

Android 应用为 **4.0.0 / versionCode 8**，最低 API 26，目标 API 35，仅提供 arm64-v8a。**沿用 v3.2.0/v3.3.0 发布签名，可直接覆盖升级，无需卸载。** 建议先导出公钥和加密 NKPR 私钥，验证备份并保留私钥密码。

仅旧签名 v3.1.x 用户需要在备份验证后卸载重装；卸载会删除内部密钥与数据，没有可用私钥或忘记密码将无法恢复解密。指纹不能恢复密钥。历史签名迁移见 [v3.2.0](https://github.com/Shixiaoshi0417/NekoKEM/blob/main/release/v3.2.0.md)。

### 格式、安全边界与兼容性

- **Core 4.0 新增 NKEM v4，NKEM v3 与 NKPR v1 不变**。X448 + ML-KEM-1024、HKDF-SHA512、AES-256-GCM、v3 header/AAD、KDF 输入与 domain、nonce/tag、指纹与 GCM 长度限制保持原有要求。NKEM v1/v2 不再支持。
- NKEM v4 会暴露接收方数量（不暴露身份）和文件长度。NKEM 不认证发送者：v4 的接收方共享文件密钥，任一接收方都能复用同一接收方列表制作新文件，接收方列表不能证明发件人。v4 隐藏的是哪条记录属于哪把私钥，而不是某把私钥能否解开文件。
- NKPR 仍使用 Argon2id **64 MiB、3 次迭代、并行度 4**，不降低密码成本；随机性、认证、敏感缓冲区清理和认证后提交规则保持不变。
- Windows 10/11 x64 保留本地固定 NTFS、所有者/ACL/可信父目录检查，以及网络、设备、ADS、重解析点拒绝。Windows CLI/GUI **没有 Authenticode 签名**；验证 Microsoft SDK loader 不代表应用已签名。GUI 需要 WebView2 Runtime。
- macOS 面向原生 M 系列 arm64，不提供 Intel/Rosetta 包。部署目标为 macOS 11.0，实际原生验证于 macOS 15；不等同于已验证 macOS 11.0 实机或每代芯片。包使用 **ad-hoc hardened-runtime 签名，没有 Developer ID 和 Apple 公证**，不能证明发布者身份或保证 Gatekeeper 放行。
- Linux GUI 构建基线为 Ubuntu 24.04，RPM 另在 Fedora 44 原生容器验证。需要 glibc 2.39+、GTK3 和 WebKitGTK 4.1；RPM 没有开发者 GPG 签名。X11 窗口检查不代表所有发行版或 Wayland 实机兼容。静态 Linux CLI 包继续提供。
- GUI 的 JavaScript/IPC 可能产生临时字符串副本，不能保证 WebView 堆可靠清零。成对文件提交不具备跨文件崩溃原子性；Windows 断电持久性、进程死亡、真实 SAF provider、并发修改和物理擦除仍有文档所述边界。不承诺跨系统或硬件性能相同。

本项目仍是实验性工具，**没有经过独立专业安全审计，不应视为生产级软件，不应用于保护重要或敏感数据**。

## English

### What's new

v4.0.0 adds multi-recipient encryption: one file can be encrypted for up to 64 recipients, each of whom decrypts it with their own private key while nobody else can. Such files use the new NKEM v4 container, available in the desktop GUI, on Android and in the CLI. Android and every CLI/GUI application are version 4.0.0; Core is now 4.0.

- **Multi-recipient encryption**: in the desktop GUI, tick several contacts on the Public-key contacts page and choose Encrypt for selected, or tick recipients in the encryption page's recipient list; the footer shows whether v3 or v4 will be written. On Android, tick Select as recipient on the Public-key contacts page and choose Encrypt for Selected Recipients; the Files page lists every recipient, and ticking alone never changes the current encryption key. On the CLI, list several public keys after the usual encryption command: `nekokem encrypt hybrid <input> <output> <key1> <key2> ...`.
- **One recipient still writes v3**: encrypting for a single recipient keeps writing NKEM v3, which older releases read; two or more recipients produce one NKEM v4 file. Decryption on every platform detects v3 and v4 automatically.
- **Any failure fails the whole operation**: before encryption, every contact is re-read and its public key and fingerprint are re-validated by Core. A missing, damaged or mismatched contact fails the whole operation without creating output and is named in the error; **no recipient is skipped or replaced by another public key**. Duplicate keys, more than 64 recipients, and two keys sharing either key component are refused.
- **NKEM v4 format**: file data is encrypted once under a random file key. Each recipient has one entry holding an X448 + ML-KEM-1024 encapsulation and the file key wrapped with AES-256-GCM; the wrap key comes from HKDF-SHA512 and binds the X448 exchange as X-Wing does. An HMAC-SHA512 header MAC commits to the file key so every recipient decrypts the same content. The full specification is [`docs/NKEM-v4.md`](../docs/NKEM-v4.md).
- **Decryption does not reveal which entry is whose**: entries carry no recipient identifier. Decryption tries every entry, including after a match. "Not for this key" and "file modified" report the same error and take the same time, so neither shows which entry belongs to which key. A malformed entry rejects the whole file, and key loading refuses the one degenerate X448 private key.
- **Pre-release review**: NKEM v4 went through two rounds of AI-assisted security review before release. They raised one Medium, five Info and one Low finding, all fixed or documented. This **is not an independent professional security audit**.
- **Tests**: new Core multi-recipient tests (Linux ASan/UBSan with leak checks, macOS, Windows) include an independent v4 encoder written from the specification, malicious-file construction, 20+ byte-level tamper offsets and error-uniformity checks. Parser and AFL++ seeds cover v4. CLI, desktop Rust/Vitest/Playwright and Android API 26/35 device tests cover multi-recipient encryption. The Android contacts UI test now refreshes accessibility nodes before use and waits for scrolled content to move, fixing intermittent failures on slow emulators.

### Compatibility notice

- NekoKEM **v3.3.2 and earlier cannot open NKEM v4 files**. Before sending a multi-recipient file, make sure its recipients run v4.0.0 or later.
- v4.0.0 decrypts every earlier NKEM v3 file. NKEM v3, NKPR v1, the public-key format and fingerprint calculation are unchanged, so existing keys keep working.

### Updating Android

Android is **4.0.0 / versionCode 8**, minimum API 26, targeting API 35, with arm64-v8a only. **The v3.2.0/v3.3.0 release signer is retained, allowing an in-place update without uninstalling.** Back up the public key and encrypted NKPR private key, verify those backups and retain the private-key password first.

Only old-signer v3.1.x installations need verified backups followed by uninstall/reinstall. Uninstalling deletes private keys and data; without a usable private key or its password, decryption cannot be recovered. Fingerprints cannot restore keys. Historical signing migration is documented in [v3.2.0](https://github.com/Shixiaoshi0417/NekoKEM/blob/main/release/v3.2.0.md).

### Formats, security boundaries and compatibility

- **Core 4.0 adds NKEM v4; NKEM v3 and NKPR v1 are unchanged**. X448 + ML-KEM-1024, HKDF-SHA512, AES-256-GCM, v3 headers/AAD, KDF inputs/domains, nonce/tag, fingerprints and GCM length limits retain their requirements. NKEM v1/v2 are no longer supported.
- NKEM v4 reveals the number of recipients (not who they are) and the file length. NKEM does not authenticate senders: v4 recipients share the file key, so any recipient can create a new file reusing the same recipient list, and the list does not prove who sent a file. v4 hides which entry belongs to which key, not whether a key can decrypt the file.
- NKPR still uses Argon2id with **64 MiB, 3 iterations and parallelism 4**, without reducing password cost. Randomness, authentication, sensitive-buffer cleanup and authenticated output commits retain their requirements.
- Windows 10/11 x64 retains local fixed NTFS, ownership/ACL/trusted-ancestor checks and rejection of network/device/ADS/reparse paths. Windows CLI/GUI are **not Authenticode signed**; verifying the Microsoft SDK loader does not sign the applications. The GUI requires WebView2 Runtime.
- macOS targets native M-series arm64, without Intel/Rosetta packages. The deployment target is macOS 11.0; native verification runs on macOS 15, not physical macOS 11.0 hardware or every chip generation. Packages use **ad-hoc hardened-runtime signatures without Developer ID or Apple notarization**, so they do not authenticate the publisher or guarantee Gatekeeper acceptance.
- Linux GUI builds use Ubuntu 24.04; RPM is additionally verified in native Fedora 44 containers. glibc 2.39+, GTK3 and WebKitGTK 4.1 are required. RPM is not developer GPG signed. X11 checks do not establish compatibility with every distribution or physical Wayland session. Static Linux CLI packages remain available.
- JavaScript/IPC may create temporary string copies, so reliable WebView heap zeroization is not guaranteed. Paired-file commits are not crash atomic across files. Windows power-loss durability, process death, real SAF providers, concurrent modification and physical erasure retain documented limits. Identical performance across systems or hardware is not promised.

This remains experimental software. **It has not undergone an independent professional security audit, must not be considered production-grade, and must not be used to protect important or sensitive data.**
