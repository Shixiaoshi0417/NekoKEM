# NekoKEM v5.0.0

## 简体中文

### 本版更新

本版加入发送方签名。Android 与各平台 CLI/GUI 统一为 **5.0.0**，Core 升级为 **5.0**。新加密的文件默认是带签名的 **NKEM v5**，接收方可以确认文件来自谁、是否被改动。格式说明见 [NKEM v5](../docs/NKEM-v5.md)。

- **默认签名**：新的身份密钥包含 X448 + ML-KEM-1024 加密密钥，以及 Ed448 + ML-DSA-87 签名密钥（NKPR v2 私钥）。加密时用你的私钥对整个文件做混合签名，两种签名都必须有效。签名者身份使用明确的二进制规范编码（NKID），指纹为其 SHA-256。
- **验签由 Core 执行**：解密时 Core 先验证签名，再与你信任的公钥（本机密钥和已保存的联系人）比对，结果为“可信”“签名有效但签名者不在联系人中”或“未签名”。「只接受已签名文件」等策略也由 Core 强制执行，签名无效或不满足策略时不会写入任何输出。
- **不签名加密（兼容旧版）**：仅在接收方使用 NekoKEM 4.x 或更早版本时需要。该选项只在设置中提供，默认关闭；开启时会弹出红色警告，默认选中「取消」。开启期间，设置页和加密页显示红字“接收方无法确认文件来自你”，加密结果标为“未签名”。CLI 对应 `encrypt --unsigned`。
- **旧密钥升级**：NekoKEM 4.x 的密钥对可就地升级为身份密钥，加密密钥、密码和旧文件都不变，旧版指纹仍会显示。身份密钥可导出只含加密部分的旧版公钥，供 4.x 接收方使用。CLI 命令为 `upgrade-key` 和 `export-legacy-public-key`。
- **联系人**：同一个人的旧版公钥被身份公钥替换时仍是一个联系人，备注保留；联系人会标明能否验证签名。
- **CLI**：`decrypt` 新增 `--trust <公钥>`（可多次）、`--require-signature`、`--require-trusted` 和 `--save-signer <路径>`，并显示签名状态和签名者指纹；`encrypt` 新增 `--sign-key <私钥>`。

### 兼容性与升级

- Android **5.0.0 / versionCode 15**，最低 API 26、目标 API 36，仅 arm64-v8a。沿用 v3.2.0/v3.3.0 签名，可直接覆盖升级；建议先备份公钥、加密 NKPR 私钥并验证密码。
- 5.0.0 可解密 NKEM v3/v4/v5，读取 NKPR v1/v2 以及两段式或四段式公钥。**NekoKEM 4.x 及更早版本无法读取 NKEM v5、NKPR v2 或四段式公钥**：给仍在使用旧版的接收方发送文件时，请开启「不签名加密」，并让对方使用你导出的旧版公钥。
- 升级旧密钥前请先导出两个密钥的备份。升级后的私钥是 NKPR v2，4.x 无法再读取它：4.x 会报告「私钥密码错误或 NKPR 数据损坏」，但这并不是密码问题，请改用 5.0.0 或更高版本。
- 未签名的 NKEM v3/v4 仍不认证发送者。AES-GCM 不提供密钥承诺性。OpenSSL 固定为 4.0.3，Argon2id 保持 64 MiB、3 次迭代、并行度 4。

### 平台与验证边界

- Windows 10/11 x64：CLI/GUI EXE 无 Authenticode 签名；GUI 需要 WebView2 Runtime。保留本地固定 NTFS、私有 ACL 与路径检查。
- macOS Apple Silicon arm64：部署目标 11.0，实际原生 CI 基线 macOS 15；不提供 Intel/Rosetta 构建。使用 ad-hoc hardened-runtime 签名，没有 Developer ID 或 Apple 公证。
- Linux GUI：Ubuntu 24.04 构建，Fedora 44 原生容器验证 RPM；需要 glibc 2.39+、GTK3、WebKitGTK 4.1。RPM 无开发者 GPG 签名；X11 启动检查不代表所有发行版或 Wayland 实机。静态 CLI 继续提供。

本项目仍是实验性工具，未经过独立专业安全审计，不应视为生产级软件或用于保护重要、敏感数据。

## English

### What's new

This release adds sender signatures. Android and every CLI/GUI application are **5.0.0**, and Core moves to **5.0**. Newly encrypted files are signed **NKEM v5** by default, so recipients can confirm who sent a file and that it was not changed. See the [NKEM v5 specification](../docs/NKEM-v5.md).

- **Signed by default**: new identity keys hold X448 + ML-KEM-1024 encryption keys and Ed448 + ML-DSA-87 signing keys (an NKPR v2 private key). Encryption signs the whole file with both algorithms, and both signatures must be valid. The signer's identity has an explicit canonical binary encoding (NKID), and its fingerprint is the SHA-256 of that encoding.
- **Core verifies**: decryption verifies the signature in Core, then matches the signer against the keys you trust (this device's key and saved contacts). The result is trusted, valid from a signer not in your contacts, or unsigned. Core also enforces policies such as Accept only signed files; an invalid signature or an unmet policy writes no output.
- **Encrypt without signing (legacy compatible)**: needed only for recipients on NekoKEM 4.x or earlier. It is a Settings option, off by default. Turning it on shows a red warning with Cancel focused. While it is on, Settings and the encrypt page show the red warning "Recipients cannot confirm the file came from you", and results are marked Unsigned. The CLI equivalent is `encrypt --unsigned`.
- **Upgrading old keys**: a NekoKEM 4.x key pair upgrades in place to an identity key. Its encryption keys, password and old files stay the same, and its legacy fingerprint is still shown. An identity key can export a legacy public key with only the encryption components for 4.x recipients. The CLI commands are `upgrade-key` and `export-legacy-public-key`.
- **Contacts**: replacing a person's legacy public key with their identity key keeps one contact and its note, and every contact shows whether it verifies signatures.
- **CLI**: `decrypt` gains `--trust <public key>` (repeatable), `--require-signature`, `--require-trusted` and `--save-signer <path>`, and shows the signature status and signer fingerprint; `encrypt` gains `--sign-key <private key>`.

### Compatibility and upgrading

- Android **5.0.0 / versionCode 15**, minimum API 26, target API 36, arm64-v8a only. The v3.2.0/v3.3.0 signer is retained for in-place updates. Back up public and encrypted NKPR private keys and verify the password first.
- 5.0.0 decrypts NKEM v3/v4/v5 and reads NKPR v1/v2 and two- or four-component public keys. **NekoKEM 4.x and earlier cannot read NKEM v5, NKPR v2 or four-component public keys**: for recipients still on an old version, turn on Encrypt without signing and have them use your exported legacy public key.
- Export a backup of both keys before upgrading an old key. The upgraded private key is NKPR v2, which 4.x can no longer read: 4.x reports "Private-key password is incorrect or NKPR data is corrupted", but the password is not the problem; use 5.0.0 or later.
- Unsigned NKEM v3/v4 still does not authenticate senders. AES-GCM provides no key commitment. OpenSSL stays pinned to 4.0.3 and Argon2id remains 64 MiB, three iterations, parallelism four.

### Platform and validation boundaries

- Windows 10/11 x64: CLI/GUI EXEs are not Authenticode signed; GUI needs WebView2 Runtime. Local fixed NTFS, private ACL and path checks remain.
- macOS Apple Silicon arm64: deployment target 11.0, native CI baseline macOS 15, no Intel/Rosetta builds. Ad-hoc hardened-runtime signatures are used, without Developer ID or Apple notarization.
- Linux GUI: built on Ubuntu 24.04, RPM tested in native Fedora 44 containers; requires glibc 2.39+, GTK3 and WebKitGTK 4.1. RPMs are not developer-GPG-signed. X11 launch tests do not establish every distribution or physical Wayland session. Static CLI packages remain available.

This remains an experimental tool without an independent professional security audit; it is not production-grade software and should not protect important or sensitive data.
