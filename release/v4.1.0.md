# NekoKEM v4.1.0

## 简体中文

### 本版更新

v4.1.0 在 v4.0.1 安全修复的基础上补齐使用体验。文件格式、密码参数和公钥指纹均不变。Android 与所有 CLI/GUI 应用统一为 4.1.0，Core 仍为 4.0；Android 应用功能与 v4.0.1 相同。

- **桌面 GUI 可以替换密钥**：v4.0.1 起生成密钥不再覆盖已有密钥，但桌面 GUI 之前只能报错，用户需要手动删除文件或改用 CLI。现在 Core 报告所选路径已有密钥后，生成页会提供“替换已有的密钥文件”选项，并提示旧私钥会被删除、用旧公钥加密的文件将无法再解密。勾选后按钮变为“替换密钥”，由 Core 的替换接口完成提交。该选项只对一次操作有效，修改任一路径或离开页面即撤销。
- **回滚保留备份时说明位置**：成对提交回滚但无法放回旧文件时（例如另一个程序已替换刚发布的密钥，或恢复失败），旧内容会保留在 `.bak` 文件中。之前只显示通用的提交错误，现在 Linux、macOS 和 Windows 都会提示“<路径> 的原有内容已保留为 <备份>”，CLI 五种语言均已翻译。Windows 的成对提交经核查只通过本进程创建文件的句柄回滚，恢复时不替换已有文件，不会删除其他写入者的文件。
- **Android 测试覆盖 API 29**：CI 的真实设备测试新增 API 29，与 API 26、35 一起覆盖原子“不覆盖”发布（Android 禁止应用创建硬链接）和每页独立缓存。
- **测试**：新增桌面 Rust 与 Vitest 用例，覆盖拒绝覆盖、确认替换、选项撤销和非生成请求拒绝 `replace`；新增文件事务测试，在两次发布之间让另一写入者替换已发布的公钥，验证对方文件保留、私钥不变、备份中为旧公钥，分别覆盖有硬链接和无硬链接两种情况。

### 兼容性提示

- 文件格式不变：v4.1.0、v4.0.1 与 v4.0.0 可互相解密 NKEM v3/v4 文件，NKPR v1 私钥和现有公钥照常使用。v3.3.2 及更早版本仍无法打开 NKEM v4 文件。
- 生成密钥仍不会自行覆盖已有密钥：CLI 使用 `keygen --replace`，Android 先请求确认，桌面 GUI 需要勾选“替换已有的密钥文件”。替换后旧私钥会被删除，用旧公钥加密的文件将无法再解密，执行前请备份旧密钥。
- POSIX 系统上，成对生成密钥会在密钥目录留下 `0600` 锁文件 `.nekokem-pair.lock`，可以保留；操作运行期间不要删除。

### Android 升级

Android 应用为 **4.1.0 / versionCode 10**，最低 API 26，目标 API 35，仅提供 arm64-v8a。**沿用 v3.2.0/v3.3.0 发布签名，可直接覆盖升级，无需卸载。** 建议先导出公钥和加密 NKPR 私钥，验证备份并保留私钥密码。

仅旧签名 v3.1.x 用户需要在备份验证后卸载重装；卸载会删除内部密钥与数据，没有可用私钥或忘记密码将无法恢复解密。指纹不能恢复密钥。历史签名迁移见 [v3.2.0](https://github.com/Shixiaoshi0417/NekoKEM/blob/main/release/v3.2.0.md)。

### 格式、安全边界与兼容性

- **Core 仍为 4.0，NKEM v3、NKEM v4 与 NKPR v1 均不变**。X448 + ML-KEM-1024、HKDF-SHA512、AES-256-GCM、v3 header/AAD、KDF 输入与 domain、nonce/tag、指纹与 GCM 长度限制保持原有要求。NKEM v1/v2 不再支持。
- NKEM v4 会暴露接收方数量（不暴露身份）和文件长度。NKEM 不认证发送者：v4 的接收方共享文件密钥，任一接收方都能复用同一接收方列表制作新文件，接收方列表不能证明发件人。v4 隐藏的是哪条记录属于哪把私钥，而不是某把私钥能否解开文件。
- NKPR 仍使用 Argon2id **64 MiB、3 次迭代、并行度 4**，不降低密码成本；随机性、认证、敏感缓冲区清理和认证后提交规则保持不变。
- Windows 10/11 x64 保留本地固定 NTFS、所有者/ACL/可信父目录检查，以及网络、设备、ADS、重解析点拒绝。Windows CLI/GUI **没有 Authenticode 签名**；验证 Microsoft SDK loader 不代表应用已签名。GUI 需要 WebView2 Runtime。
- macOS 面向原生 M 系列 arm64，不提供 Intel/Rosetta 包。部署目标为 macOS 11.0，实际原生验证于 macOS 15；不等同于已验证 macOS 11.0 实机或每代芯片。包使用 **ad-hoc hardened-runtime 签名，没有 Developer ID 和 Apple 公证**，不能证明发布者身份或保证 Gatekeeper 放行。
- Linux GUI 构建基线为 Ubuntu 24.04，RPM 另在 Fedora 44 原生容器验证。需要 glibc 2.39+、GTK3 和 WebKitGTK 4.1；RPM 没有开发者 GPG 签名。X11 窗口检查不代表所有发行版或 Wayland 实机兼容。静态 Linux CLI 包继续提供。
- GUI 的 JavaScript/IPC 可能产生临时字符串副本，不能保证 WebView 堆可靠清零。成对文件提交不具备跨文件崩溃原子性；Windows 断电持久性、进程死亡、真实 SAF provider、并发修改和物理擦除仍有文档所述边界。不承诺跨系统或硬件性能相同。

本项目仍是实验性工具，**没有经过独立专业安全审计，不应视为生产级软件，不应用于保护重要或敏感数据**。

## English

### What's new

v4.1.0 builds on the v4.0.1 security fixes to round out everyday use. File formats, cryptographic parameters and public-key fingerprints are unchanged. Android and every CLI/GUI application are version 4.1.0; Core remains 4.0, and the Android app behaves as in v4.0.1.

- **The desktop GUI can replace keys**: since v4.0.1 key generation no longer overwrites existing keys, but the desktop GUI could only report the refusal, leaving users to delete files by hand or use the CLI. Once Core reports existing keys at the chosen paths, the keygen page now offers "Replace the existing key files" with a warning that the old private key is deleted and files encrypted for the old public key can then no longer be decrypted. Ticking it changes the button to "Replace keys", and Core's replacement interface commits the new pair. The option covers one run and is withdrawn when either path changes or the page is left.
- **Rollback names the kept backup**: when a paired commit rolls back but cannot put the old file back (for example because another program replaced the key just published, or the restore failed), the old contents stay in a `.bak` file. Only a generic commit error was shown before; Linux, macOS and Windows now print "The previous contents of <path> are kept as <backup>", translated in all five CLI languages. The Windows paired commit was reviewed: it rolls back only through handles of files this process created and restores without replacement, so it never removes another writer's file.
- **Android tests cover API 29**: CI's real-device tests add API 29, which together with API 26 and 35 exercises atomic no-replace publication (Android forbids apps to create hard links) and per-page caches.
- **Tests**: new desktop Rust and Vitest cases cover the refused overwrite, confirmed replacement, withdrawal of the option and rejection of `replace` outside keygen. A new file-transaction test has another writer replace the published public key between the two publications and checks that its file stays, the private key is untouched and the backup holds the old key, with and without hard links.

### Compatibility notice

- File formats are unchanged: v4.1.0, v4.0.1 and v4.0.0 decrypt each other's NKEM v3/v4 files, and NKPR v1 private keys and existing public keys keep working. v3.3.2 and earlier still cannot open NKEM v4 files.
- Key generation still never overwrites existing keys on its own: use `keygen --replace` in the CLI; Android asks for confirmation first, and the desktop GUI needs "Replace the existing key files" ticked. Replacing deletes the old private key, so files encrypted for the old public key can no longer be decrypted; back up the old keys first.
- On POSIX systems, generating a key pair leaves the mode `0600` lock file `.nekokem-pair.lock` in the key directory. It can stay there; do not delete it while an operation runs.

### Updating Android

Android is **4.1.0 / versionCode 10**, minimum API 26, targeting API 35, with arm64-v8a only. **The v3.2.0/v3.3.0 release signer is retained, allowing an in-place update without uninstalling.** Back up the public key and encrypted NKPR private key, verify those backups and retain the private-key password first.

Only old-signer v3.1.x installations need verified backups followed by uninstall/reinstall. Uninstalling deletes private keys and data; without a usable private key or its password, decryption cannot be recovered. Fingerprints cannot restore keys. Historical signing migration is documented in [v3.2.0](https://github.com/Shixiaoshi0417/NekoKEM/blob/main/release/v3.2.0.md).

### Formats, security boundaries and compatibility

- **Core remains 4.0; NKEM v3, NKEM v4 and NKPR v1 are unchanged**. X448 + ML-KEM-1024, HKDF-SHA512, AES-256-GCM, v3 headers/AAD, KDF inputs/domains, nonce/tag, fingerprints and GCM length limits retain their requirements. NKEM v1/v2 are no longer supported.
- NKEM v4 reveals the number of recipients (not who they are) and the file length. NKEM does not authenticate senders: v4 recipients share the file key, so any recipient can create a new file reusing the same recipient list, and the list does not prove who sent a file. v4 hides which entry belongs to which key, not whether a key can decrypt the file.
- NKPR still uses Argon2id with **64 MiB, 3 iterations and parallelism 4**, without reducing password cost. Randomness, authentication, sensitive-buffer cleanup and authenticated output commits retain their requirements.
- Windows 10/11 x64 retains local fixed NTFS, ownership/ACL/trusted-ancestor checks and rejection of network/device/ADS/reparse paths. Windows CLI/GUI are **not Authenticode signed**; verifying the Microsoft SDK loader does not sign the applications. The GUI requires WebView2 Runtime.
- macOS targets native M-series arm64, without Intel/Rosetta packages. The deployment target is macOS 11.0; native verification runs on macOS 15, not physical macOS 11.0 hardware or every chip generation. Packages use **ad-hoc hardened-runtime signatures without Developer ID or Apple notarization**, so they do not authenticate the publisher or guarantee Gatekeeper acceptance.
- Linux GUI builds use Ubuntu 24.04; RPM is additionally verified in native Fedora 44 containers. glibc 2.39+, GTK3 and WebKitGTK 4.1 are required. RPM is not developer GPG signed. X11 checks do not establish compatibility with every distribution or physical Wayland session. Static Linux CLI packages remain available.
- JavaScript/IPC may create temporary string copies, so reliable WebView heap zeroization is not guaranteed. Paired-file commits are not crash atomic across files. Windows power-loss durability, process death, real SAF providers, concurrent modification and physical erasure retain documented limits. Identical performance across systems or hardware is not promised.

This remains experimental software. **It has not undergone an independent professional security audit, must not be considered production-grade, and must not be used to protect important or sensitive data.**
